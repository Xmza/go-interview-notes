## Как применить принципы SOLID в Go? (Примеры)

SOLID — это 5 принципов ООП, которые в Go реализуются через интерфейсы и композицию.

1.  **S (SRP) — Single Responsibility**: Структура/функция должна делать что-то одно.
    *   *В Go:* Не делайте "God-struct", которая и сохраняет в БД, и шлет HTTP, и считает логику. Разбейте на разные пакеты/типы.
2.  **O (OCP) — Open/Closed**: Открыт для расширения, закрыт для изменения.
    *   *В Go:* Используйте интерфейсы. Вы можете добавить новую реализацию интерфейса `Storage`, не меняя код бизнес-логики, который этот интерфейс использует.
3.  **L (LSP) — Liskov Substitution**: Наследники должны заменять родителей без поломки логики.
    *   *В Go:* Так как нет классического наследования, принцип сводится к корректной реализации интерфейсов. Если `interface` требует `Write`, реализация не должна кидать панику вместо записи.
4.  **I (ISP) — Interface Segregation**: Много маленьких интерфейсов лучше, чем один большой.
    *   *В Go:* **Ключевой принцип**. Лучше `Reader` и `Writer` отдельно, чем огромный `ReadWriteCloserSeeker`. Клиент должен зависеть только от тех методов, которые использует.
5.  **D (DIP) — Dependency Inversion**: Зависеть от абстракций, а не от деталей.
    *   *В Go:* Принимайте в функции интерфейсы (`Repository`), а не конкретные структуры (`*PostgresDB`).

<pre>
В Go самый важный принцип — Interface Segregation. Определяйте интерфейсы по месту использования (там, где они нужны), и делайте их максимально маленькими (1-2 метода).
</pre>

## Dependency Injection в Go: зачем нужно и какие есть библиотеки (Wire, Dig)?

Dependency Injection (DI) — это когда объекты не создают свои зависимости сами, а получают их извне (обычно через конструктор).

**Без DI (Плохо для тестов):**
```go
func NewService() *Service {
    db := ConnectToDB() // Жесткая связь
    return &Service{db: db}
}
```

**С DI (Хорошо):**
```go
func NewService(db Repository) *Service {
    return &Service{db: db}
}
```

**Библиотеки:**
1.  **Ручной DI (Manual Wiring):** Самый популярный в Go. Вы создаете все зависимости в `main.go` и прокидываете их. Просто, понятно, но много бойлерплейта.
2.  **Google Wire:** (Code generation). Вы описываете зависимости, а Wire генерирует код инициализации во время компиляции. Проверяет ошибки типов до запуска.
3.  **Uber Dig / Facebook Inject:** (Reflection based). Внедряет зависимости в рантайме. Менее популярен из-за магии и возможных ошибок в рантайме.

<pre>
В Go сообществе принят явный (manual) DI. Если проект очень большой, используют Google Wire (compile-time safety). Избегайте reflection-based DI контейнеров.
</pre>

## Чистая архитектура (Clean Architecture): слои, где писать бизнес-логику?

Суть: Разделение приложения на слои, где зависимости направлены только **внутрь**. Внешние слои знают о внутренних, внутренние о внешних — нет.

```perl
      Внешний мир (HTTP, GRPC, CLI)
            ↓     ↑
      +-------------------+
      |  Interface Adapters (Handlers) |
      +-------------------+
            ↓     ↑
      +-------------------+
      |   Use Cases (Service)      |  <-- БИЗНЕС-ЛОГИКА ТУТ
      +-------------------+
            ↓     ↑
      +-------------------+
      |   Entities (Domain)        |  <-- Чистые структуры данных
      +-------------------+
```

1.  **Domain (Entities):** Основные структуры (User, Order). Не зависят ни от чего.
2.  **Use Cases (Service):** Сценарии работы (CreateUser, PayOrder). Оперируют доменом. Определяют интерфейсы репозиториев (`UserRepository`).
3.  **Interface Adapters:** Реализация интерфейсов (PostgresRepo, RedisCache) и HTTP хендлеры. Преобразуют данные из формата БД/HTTP в формат Use Cases.
4.  **Frameworks/Drivers:** БД, веб-фреймворк, конфиги.

<pre>
Бизнес-логика живет в Use Cases (Service). Она не должна знать про SQL, JSON или HTTP. Она работает с интерфейсами репозиториев.
</pre>

## Hexagonal Architecture (Ports and Adapters) простыми словами

Это вариация Чистой Архитектуры.
Приложение — это шестиугольник (ядро).
В него ведут **Порты** (Интерфейсы).
К портам подключаются **Адаптеры** (Реализации).

*   **Primary Adapters (Driving):** То, что дергает приложение (HTTP Handler, CLI Command).
*   **Secondary Adapters (Driven):** То, что дергает само приложение (Postgres, SMTP server).

```go
// PORT (Interface) - внутри ядра
type UserRepo interface {
    Save(u User) error
}

// ADAPTER (Implementation) - снаружи
type PostgresRepo struct { ... }
func (p *PostgresRepo) Save(u User) error { ... }
```

<pre>
Гексагональная архитектура позволяет менять БД, фреймворки или внешние API, просто подменяя Адаптеры, не трогая ядро (бизнес-логику).
</pre>

## Разница между Monolith и Microservices: когда стоит пилить монолит?

1.  **Monolith (Монолит):**
    *   *Плюсы:* Простота разработки, деплоя, отладки. Одна БД, транзакции работают "из коробки" (ACID). Быстрое общение между компонентами (вызов функции).
    *   *Минусы:* Сложно масштабировать отдельные части. При падении падает всё. "Spaghetti code" со временем.
2.  **Microservices (Микросервисы):**
    *   *Плюсы:* Независимый деплой и масштабирование. Можно писать на разных языках. Отказоустойчивость (упал сервис оплаты — каталог работает).
    *   *Минусы:* **Распределенная система** — это очень сложно (network latency, distributed transactions, eventual consistency). Нужен DevOps (K8s, CI/CD).

**Когда выбирать Монолит?**
Всегда начинайте с **модульного монолита**. Пока у вас нет >50 разработчиков или специфических требований к нагрузке разных модулей, микросервисы принесут только боль (over-engineering).

## Структура проекта: Standard Go Project Layout (cmd, internal, pkg)

Неофициальный, но самый популярный стандарт:

```text
/project-root
├── /cmd
│   └── /app          // Точка входа (main.go). Тут wiring зависимостей.
├── /internal         // Приватный код. Нельзя импортировать из других проектов.
│   ├── /domain       // Сущности
│   ├── /service      // Бизнес-логика
│   └── /repository   // Работа с БД
├── /pkg              // Публичные библиотеки (можно использовать в других проектах)
│   └── /logger       // Например, кастомный логгер
├── /api              // Proto файлы, Swagger
├── /configs          // Конфигурационные файлы
├── go.mod
└── Makefile
```

<pre>
Используйте /internal для всего кода приложения, чтобы никто случайно не импортировал ваши кишки как библиотеку. В /cmd держите только main файлы.
</pre>

## Domain Driven Design (DDD) в Go: Агрегаты, Value Objects, Entities

DDD — это подход к проектированию сложной бизнес-логики.

1.  **Entity (Сущность):** Объект, у которого есть **уникальный ID**. Даже если данные одинаковые, разные ID означают разные объекты. (Пример: `User`, `Order`). В Go это обычно структуры, передаваемые по указателю.
2.  **Value Object (Объект-значение):** Объект без ID, определяется только своими данными. Если данные равны — объекты равны. Неизменяемы (Immutable). (Пример: `Money`, `Coordinates`, `Email`). В Go это структуры, передаваемые по значению.
3.  **Aggregate (Агрегат):** Группа объектов, которые рассматриваются как единое целое. У агрегата есть **Aggregate Root** (Корень).
    *   *Правило:* Изменять данные внутри агрегата можно только через методы Корня. Транзакция БД должна сохранять Агрегат целиком.

<pre>
В Go DDD часто упрощают. Главное: выделять доменную модель (чистые структуры) отдельно от логики хранения и отображения.
</pre>
