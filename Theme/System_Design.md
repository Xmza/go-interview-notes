## Идемпотентность (Idempotency): Что это и почему это критично для API?

**Идемпотентность** — свойство операции давать **одинаковый результат** при многократном повторении.

*   *Пример:* `a = 10` (Идемпотентно, сколько ни присваивай, будет 10).
*   *Пример:* `a++` (НЕ идемпотентно, каждый раз значение растет).

**Зачем в API (особенно платежи):**
Клиент послал запрос "Списать 100 рублей". Интернет моргнул. Клиент не получил ответ. Клиент (или прокси) повторяет запрос (Retry).
Без идемпотентности вы спишете 200 рублей.

**Как реализовать:**
Клиент шлет уникальный `Idempotency-Key` (UUID) в хедере. Сервер проверяет: если ключ уже обрабатывался, он не делает операцию второй раз, а сразу отдает сохраненный результат успеха.

## CAP теорема простыми словами (CP vs AP системы)

В распределенной системе невозможно гарантировать одновременно все три свойства:
1.  **C (Consistency)** — Согласованность (во всех узлах данные одинаковы в любой момент).
2.  **A (Availability)** — Доступность (система отвечает на запросы, даже если часть узлов упала).
3.  **P (Partition Tolerance)** — Устойчивость к разделению сети (система работает, если кабель между дата-центрами перерезан).

P — обязательное условие в реальности. Поэтому мы выбираем между:
*   **CP (Consistency + Partition Tolerance):** Если сеть лагает, мы **запрещаем запись**, чтобы данные не разъехались. (Пример: Банковские транзакции, MongoDB в дефолте).
*   **AP (Availability + Partition Tolerance):** Если сеть лагает, мы принимаем запись, но данные могут быть временно разными на разных узлах (Eventual Consistency). (Пример: Лайки в соцсетях, DNS, Cassandra).

## Rate Limiting: Алгоритмы (Token Bucket, Leaky Bucket)

Защита API от спама и перегрузки.

1.  **Token Bucket (Ведро с токенами):**
    *   Есть ведро емкостью N токенов.
    *   Токены капают в ведро со скоростью X в секунду.
    *   Запрос забирает 1 токен. Если ведро пустое — отказ (429 Too Many Requests).
    *   *Плюс:* Позволяет кратковременные всплески (bursts) трафика.
2.  **Leaky Bucket (Дырявое ведро):**
    *   Запросы попадают в очередь (ведро).
    *   Из очереди они выходят с фиксированной скоростью.
    *   Если очередь полна — новые отбрасываются.
    *   *Плюс:* Идеально сглаживает трафик.

## Кеширование: Стратегии (Cache-Aside, Write-Through) и проблемы (Cache Stampede)

**Стратегии:**
1.  **Cache-Aside (Lazy Loading):** Приложение читает из кеша. Если пусто -> читает из БД -> кладет в кеш -> отдает клиенту. Самая популярная.
2.  **Write-Through:** Приложение пишет сразу и в кеш, и в БД (синхронно). Данные всегда свежие, но запись медленнее.

**Cache Stampede (Thundering Herd):**
Ситуация, когда горячий ключ в кеше протухает, и 1000 одновременных запросов ломятся в БД, чтобы его обновить. БД падает.
*Решение:* Использовать мьютексы (один обновляет, остальные ждут) или вероятностное обновление (обновить кеш чуть раньше срока истечения).

## Distributed Tracing: Зачем нужен OpenTelemetry / Jaeger?

В микросервисах один запрос пользователя может породить цепочку из 20 вызовов разных сервисов (Auth -> Cart -> Payment -> Notification).
Если запрос тормозит, как понять, ГДЕ именно? Логи не помогут, они разбросаны.

**Трейсинг:**
Каждому входящему запросу присваивается `TraceID`. Этот ID передается в заголовках (`X-Trace-Id`) всем внутренним сервисам.
Система (Jaeger/Zipkin) собирает спаны (отрезки времени) со всех сервисов и строит **Граф вызова**:
*   Auth: 10ms
*   Cart: 5ms
*   **Payment: 2000ms (ВОТ ОНО!)**
*   Notification: 10ms

<pre>
Без трейсинга отладка тормозов в микросервисах невозможна.
</pre>
