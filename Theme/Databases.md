## Как работает пулинг соединений (Connection Pool) в database/sql?

Пакет `database/sql` имеет встроенный пул соединений. Когда вы делаете `sql.Open()`, соединение с БД **не открывается** сразу. Оно создается лениво при первом запросе.

1.  Когда вы делаете запрос (`db.Query`), драйвер смотрит в пул.
2.  Если есть свободное соединение (`Idle`), он берет его.
3.  Если нет — создает новое (если не достигнут лимит `MaxOpenConns`).
4.  После `rows.Close()` соединение возвращается в пул (становится `Idle`).

**Важные настройки:**
*   `db.SetMaxOpenConns(n)`: Максимальное кол-во открытых соединений.
*   `db.SetMaxIdleConns(n)`: Сколько соединений держать "про запас" в простое.
*   `db.SetConnMaxLifetime(d)`: Через сколько времени убивать соединение (важно для облачных балансировщиков).

<pre>
Всегда настраивайте лимиты пула. По умолчанию MaxOpenConns = 0 (бесконечно), что может положить базу данных при скачке трафика.
</pre>

## Как избежать SQL Injection в Go?

**Никогда** не подставляйте параметры в строку запроса через `fmt.Sprintf` или `+`.

❌ **Плохо (Injection):**
```go
query := fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", userName)
db.Query(query) // Если userName = "'; DROP TABLE users; --", будет беда.
```

✅ **Хорошо (Placeholders):**
Используйте плейсхолдеры (`?` для MySQL/SQLite, `$1` для Postgres). Драйвер сам экранирует данные.
```go
// Postgres style
db.Query("SELECT * FROM users WHERE name = $1", userName)
```

<pre>
SQL Injection происходит, когда данные интерпретируются как код. Плейсхолдеры отправляют данные отдельно от тела запроса.
</pre>

## Проблема NULL значений в SQL и как с ними работать в Go (sql.NullString vs *string)

В SQL есть `NULL`, в Go у примитивов (`int`, `string`) нет `nil`.

1.  **sql.NullString / sql.NullInt64:**
    Специальные структуры из стандартной библиотеки.
    ```go
    type User struct {
        Name sql.NullString // Valid: true/false, String: "value"
    }
    ```
    *Минус:* Неудобно работать в JSON (сериализуется как объект `{Valid: true, String: "..."}`).

2.  **Указатели (*string, *int):**
    ```go
    type User struct {
        Name *string
    }
    ```
    Если в БД `NULL`, сканер запишет `nil`.
    *Плюс:* В JSON сериализуется корректно как `null`.

<pre>
Для API и JSON удобнее использовать указатели (*string). Для внутренней логики иногда безопаснее sql.Null типы, чтобы избежать nil pointer panic.
</pre>

## Транзакции в Go: как правильно открывать, комитить и откатывать?

Транзакция гарантирует атомарность (все или ничего).

**Паттерн работы:**
```go
tx, err := db.Begin() // 1. Начинаем
if err != nil { return err }

// Важно! Defer Rollback
defer tx.Rollback() // 2. Планируем откат (если забыли сделать Commit или была паника/ошибка)

_, err = tx.Exec("UPDATE ...")
if err != nil {
    return err // Сработает defer Rollback
}

// ... другие запросы ...

if err := tx.Commit(); err != nil { // 3. Фиксируем
    return err
}
// После Commit вызов Rollback (в дефере) ничего не сделает, это безопасно.
return nil
```

<pre>
Всегда используйте defer tx.Rollback() сразу после создания транзакции. Это спасет от зависших транзакций при ошибках и паниках.
</pre>

## Подготовленные запросы (Prepared Statements): зачем нужны и как влияют на performance?

`stmt, err := db.Prepare("SELECT ... WHERE id = $1")`

1.  **Prepare:** SQL-сервер парсит запрос, строит план выполнения и кэширует его.
2.  **Execute:** Вы только шлете параметры.

**Плюсы:**
*   **Безопасность:** Защита от SQL Injection (так же, как обычные плейсхолдеры).
*   **Производительность:** Если один и тот же запрос (с разными параметрами) выполняется 1000 раз в цикле, Prepare сэкономит время на парсинг SQL на стороне базы.

**Минусы:** Лишний round-trip (сетевой запрос) на создание Statement, если вы выполняете запрос всего один раз.

## ORM vs Raw SQL vs Query Builders (GORM, sqlx, Squirrel) - плюсы и минусы

1.  **GORM (ORM):**
    *   *Плюсы:* Разработка летит. Автомиграции, связи, хуки.
    *   *Минусы:* Магия, рефлексия (медленно), сложно оптимизировать сложные запросы. Трудно отлаживать.
2.  **sqlx (Расширение standard lib):**
    *   *Плюсы:* Позволяет сканировать `row` сразу в `struct` (`Select`, `Get`). Почти как нативный SQL. Быстро.
    *   *Минусы:* SQL пишешь руками (что для многих плюс).
3.  **Squirrel / Goqu (Query Builders):**
    *   *Плюсы:* Пишешь SQL кодом Go (`Select("id").From("users")`). Удобно для динамических фильтров.
4.  **Raw SQL (database/sql):**
    *   *Плюсы:* Полный контроль, макс. скорость.
    *   *Минусы:* Много кода для сканирования переменных.

<pre>
В Go принято избегать тяжелых ORM (GORM) в высоконагруженных проектах. Золотая середина — sqlx или pgx (для Postgres) + squirrel для динамики.
</pre>

## Оптимистическая и пессимистическая блокировка

Как не дать двум юзерам перезаписать данные одновременно?

1.  **Пессимистическая (SELECT FOR UPDATE):**
    *   Блокируем строку в БД на уровне транзакции. Пока мы не закончим, никто другой не может ее прочитать/изменить.
    *   *Минус:* Снижает производительность, возможны дедлоки.
2.  **Оптимистическая (Version column):**
    *   Добавляем колонку `version` (int).
    *   При обновлении проверяем: `UPDATE users SET balance = 100, version = 2 WHERE id = 1 AND version = 1`.
    *   Если `RowsAffected == 0`, значит кто-то успел изменить версию до нас. Повторяем операцию или отдаем ошибку.
    *   *Плюс:* Нет блокировок базы.

## Миграции БД: инструменты (Goose, Migrate) и стратегии

Миграции — это версионирование схемы БД (git для базы).

**Инструменты:**
*   **Goose:** Популярен, поддерживает SQL и Go файлы миграций.
*   **Golang-migrate:** Очень мощный, поддерживает кучу драйверов.

**Стратегии:**
1.  **Up & Down:** Всегда пишите `Up` (создать таблицу) и `Down` (удалить таблицу).
2.  **Backwards compatibility:** При деплое новой версии кода, старая версия кода какое-то время работает параллельно.
    *   Нельзя просто переименовать колонку.
    *   Шаг 1: Создать новую, дублировать запись в старую и новую.
    *   Шаг 2: Деплой кода, который читает из новой.
    *   Шаг 3: Удаление старой колонки.
