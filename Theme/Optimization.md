## Выравнивание структур (Memory Alignment/Padding): Как сэкономить память, просто переставив поля?

CPU читает память не побайтово, а "словами" (word), обычно по 8 байт (на 64-bit системах).
Поля в структуре выравниваются по границам слов. Если поле занимает меньше места, чем нужно для выравнивания, компилятор добавляет пустые байты — **padding**.

**Пример "плохой" структуры:**
```go
type Bad struct {
    Flag    bool  // 1 байт + 7 байт padding
    Counter int64 // 8 байт
    Active  bool  // 1 байт + 7 байт padding
}
// Размер: 24 байта (реально данных 10 байт, мусора 14 байт)
```

**Пример "хорошей" структуры:**
```go
type Good struct {
    Counter int64 // 8 байт
    Flag    bool  // 1 байт
    Active  bool  // 1 байт + 6 байт padding (в конце)
}
// Размер: 16 байт
```

<pre>
Правило: Располагайте поля от самого большого размера к самому маленькому (int64 -> int -> bool). Это бесплатно экономит RAM.
Утилита для проверки: fieldalignment (golang.org/x/tools/go/analysis/passes/fieldalignment).
</pre>

## Что такое False Sharing и как с ним бороться (padding в CPU cache line)?

Проблема возникает, когда две разные переменные попадают в одну **Cache Line** (обычно 64 байта) процессора.
Если Core 1 меняет переменную `A`, а Core 2 читает переменную `B` (которая лежит рядом с `A`), процессор вынужден инвалидировать кэш-линию целиком для обоих ядер. Это убивает производительность многопоточной программы.

**Решение (Padding):**
Добавляем пустые поля, чтобы отодвинуть переменные друг от друга.

```go
type NoFalseSharing struct {
    A uint64
    _ [56]byte // Padding, чтобы A и B были в разных кэш-линиях (8 + 56 = 64)
    B uint64
}
```

## Sync.Pool: Зачем нужен, как работает и когда его НЕЛЬЗЯ использовать?

`sync.Pool` — это кэш для временных объектов, чтобы снизить нагрузку на Garbage Collector (GC). Вместо аллокации нового объекта мы берем старый из пула, а потом возвращаем.

**Как работает:**
1.  `pool.Get()`: Дай объект. Если пусто — создай новый (через New).
2.  `pool.Put(x)`: Возьми объект обратно (перед этим его надо "обнулить").

**Особенность:** Пул очищается автоматически при каждом запуске GC. Вы не контролируете время жизни объектов.

**Когда НЕЛЬЗЯ:**
1.  Для хранения постоянных соединений (Database connections). Они закроются при GC.
2.  Для редко используемых объектов.

<pre>
Идеальный кейс: буферы ([]byte, bytes.Buffer) в высоконагруженных веб-серверах, которые живут только во время одного запроса.
</pre>

## Inlining функций: Что это и как посмотреть, заинлайнил ли компилятор функцию?

**Inlining** — это когда компилятор берет тело функции и вставляет его прямо в место вызова, вместо того чтобы делать реальный `CALL` (прыжок по адресу памяти).
Это быстрее (нет накладных расходов на вызов), но увеличивает размер бинарника.

Компилятор инлайнит только простые и короткие функции.

**Как проверить:**
Скомпилировать с флагом `-m` (escape analysis + inlining decisions).
```bash
go build -gcflags="-m" main.go
```
Вывод: `can inline Key ...` или `inlining call to ...`

## String Interning: Как хранить миллионы одинаковых строк и не забить память?

Если вы парсите огромный JSON/CSV, где повторяются значения (например, "City": "Moscow" миллион раз), Go создаст миллион разных строк "Moscow".

**Решение (Интернирование):**
Хранить уникальные строки в мапе и переиспользовать их.

```go
var pool = map[string]string{}

func intern(s string) string {
    if val, ok := pool[s]; ok {
        return val // Возвращаем существующую ссылку
    }
    pool[s] = s
    return s
}
```
Теперь миллион записей будут указывать на один и тот же заголовок строки в памяти.

## Zero-allocation техники: преобразование string <-> []byte без копирования

Обычное преобразование `string(bytes)` или `[]byte(str)` вызывает **копирование** памяти (так как string immutable, а slice mutable).
В критичных местах (HFT, парсеры) используют `unsafe`, чтобы подменить тип без копирования.

**String to Bytes:**
```go
func strToBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
```
*Опасно:* Нельзя менять полученный слайс, иначе будет Segfault или порча памяти (т.к. строка лежит в RO памяти).

**Bytes to String:**
```go
func bytesToStr(b []byte) string {
    return unsafe.String(unsafe.SliceData(b), len(b))
}
```
