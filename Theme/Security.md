## Как правильно хранить пароли? (bcrypt, argon2, salt)

**НИКОГДА** не храните пароли в открытом виде.
**НИКОГДА** не используйте простые хеши (MD5, SHA1, SHA256) без соли. Они ломаются по радужным таблицам мгновенно.

Используйте специальные криптографические алгоритмы с "солью" и настройкой сложности:
1.  **bcrypt:** Стандарт де-факто в Go (`golang.org/x/crypto/bcrypt`).
2.  **Argon2:** Более современный, устойчив к GPU-брутфорсу (требует много памяти).

**Пример:**
```go
hash, _ := bcrypt.GenerateFromPassword([]byte("password"), bcrypt.DefaultCost)
// Сохраняем hash в БД

// Проверка
err := bcrypt.CompareHashAndPassword(hash, []byte("inputPassword"))
```

<pre>
Соль (Salt) — случайная строка, добавляемая к паролю перед хешированием. В bcrypt соль генерируется и хранится внутри самого хеша автоматически.
</pre>

## Что такое JWT, JWE, JWS и где их хранить (Cookie vs LocalStorage)?

*   **JWT (JSON Web Token):** Стандарт токена. Состоит из Header.Payload.Signature.
*   **JWS (Signed):** Подписанный токен (данные видны всем `base64`, но их нельзя изменить). Самый частый кейс.
*   **JWE (Encrypted):** Зашифрованный токен (данные скрыты).

**Где хранить?**
1.  **LocalStorage:** Удобно (JS может читать), но **уязвимо для XSS**. Если хакер внедрит JS на сайт, он украдет токены.
2.  **HttpOnly Cookie:** JS не имеет доступа к куке. Браузер сам шлет её. **Безопасно от XSS**, но нужно защищаться от CSRF.

<pre>
Рекомендация: Refresh Token хранить в HttpOnly Cookie (строго). Access Token можно в памяти JS (ненадолго) или тоже в Cookie.
</pre>

## Защита от XSS и CSRF атак в Go веб-приложениях

1.  **XSS (Cross Site Scripting):** Внедрение вредоносного JS кода на страницу.
    *   *Защита:* Стандартный шаблонизатор `html/template` в Go **автоматически экранирует** все переменные. Не используйте `template.HTML` (raw html), если не уверены в источнике.
2.  **CSRF (Cross Site Request Forgery):** Злоумышленник делает форму на своем сайте, которая шлет POST запрос на ваш сайт (а куки юзера браузер подставляет сам).
    *   *Защита:* CSRF-токены. Сервер выдает уникальный токен в HTML-форме, и ожидает его же в POST запросе.
    *   *Cookie SameSite:* Установите атрибут `SameSite=Strict` или `Lax` для кук.

## TLS/SSL: Как поднять HTTPS сервер на Go?

В Go HTTPS поддерживается из коробки.

```go
// Простой вариант (нужны файлы сертификатов)
http.ListenAndServeTLS(":443", "cert.pem", "key.pem", nil)
```

**Auto-HTTPS (Let's Encrypt):**
Используйте библиотеку `golang.org/x/crypto/acme/autocert` или Caddy сервер перед Go.
Go может сам стучаться в Let's Encrypt и получать/обновлять сертификаты.

## Как безопасно работать с конфигами и секретами (ENV, Hashicorp Vault)?

1.  **ENV (Переменные окружения):** Самый простой способ (12-factor app). Библиотеки `godotenv`, `envconfig`.
    *   *Правило:* Никогда не коммитьте `.env` файлы с реальными паролями в Git.
2.  **Secret Managers (Hashicorp Vault, AWS Secrets Manager):** Для серьезного продакшна. Приложение при старте стучится в Vault, авторизуется и получает секреты в память. На диске пароли не лежат.

<pre>
Hardcoding (жесткое прописывание) паролей в коде — это главная дыра в безопасности. Используйте переменные окружения.
</pre>
