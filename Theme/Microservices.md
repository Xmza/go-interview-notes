## Как Go используют в микросервисной архитектуре

Go идеально подходит для микросервисов благодаря:

* **Компиляции в статический бинарь** → просто деплоить через Docker/K8s;
* **Лёгкости рантайма** → Go-сервисы запускаются быстро и потребляют мало памяти;
* **Concurrency-модели** → тысячи соединений обслуживаются параллельно;
* **Богатой стандартной библиотеке** → HTTP, gRPC, JSON, pprof, профайлинг из коробки.

Чаще всего на Go пишут:

* API-шлюзы и backend-for-frontend;
* сервисы с высокой нагрузкой (реальное время, стриминг);
* воркеры для асинхронной обработки событий.

## Как общаются микросервисы gRPC vs REST

* **REST** — HTTP + JSON, легко интегрировать, удобно дебажить, но медленнее и многословнее.
* **gRPC** — HTTP/2 + Protobuf, бинарный протокол, быстрый, поддерживает стриминг, но требует генерации кода.

## Kafka: ключевые вопросы на собеседовании

**Основное:** Kafka — распределённый commit log, заточенный под потоковую обработку данных.

**Что могут спросить:**

* Что такое *partition* и зачем он нужен?
  → Делит топик на сегменты для параллельной обработки.
* Что такое *consumer group*?
  → Группа консьюмеров, где каждый получает уникальные партиции (scalability + fault tolerance).
* Как реализовать *retries* и *dead-letter queue (DLQ)*?
  → Повторные попытки + выделенный топик для проблемных сообщений.
* Чем Kafka отличается от RabbitMQ?
  → Kafka хранит сообщения на диске и переиспользует, RabbitMQ — ориентирован на маршрутизацию и гарантированную доставку.
* Как решать проблему «consumer lag»?
  → Масштабирование consumer group, мониторинг offset’ов, тюнинг партиций.

## Redis: ключевые вопросы на собеседовании

**Основное:** Redis — in-memory хранилище, используется для кэша, pub/sub, сессий, rate limiting.

**Что могут спросить:**

* Чем Redis отличается от Memcached?
  → Redis поддерживает структуры данных (строки, списки, множества), persistence и pub/sub.
* Как реализовать *distributed lock* в Redis?
  → Через команду `SET key value NX PX <time>` или библиотеку Redlock.
* Что будет, если Redis «упадёт»?
  → Данные могут потеряться (если не настроен persistence), нужно репликация + Sentinel/Cluster.
* Как бороться с проблемой «cache stampede»?
  → Использовать `TTL` + случайный дрифт, double-checked locking.
* Чем опасен долгий pipeline/transaction в Redis?
  → Блокировка event loop, задержки для других клиентов.

## Graceful shutdown микросервиса

Корректное завершение микросервиса важно для стабильности.

**Этапы:**

1. Ловим сигналы `SIGTERM`, `SIGINT`.
2. Используем `context.WithTimeout` для ограничения времени завершения.
3. Закрываем соединения (DB, Kafka, Redis, HTTP).
4. Ждём завершения горутин.
